# Configuration files and Git tracking rules

**English** | [简体中文](README.zh-CN.md)

This repository follows these rules uniformly:

- `*.example`: copyable configuration templates. They must be tracked by Git and must never contain a real password, token or private key.
- `*.template`: static templates rendered by a script. They must be tracked by Git.
- Static cluster configuration: files that are identical across all deployments are tracked by Git.
- Active configuration: contains site addresses, real hardware parameters or local adjustments. It stays on the deployment host only and is ignored by `.gitignore`.
- Generated configuration: regenerated by a script, never committed.
- Keys and passwords: never committed, and never passed through a public NAS directory or a chat.

## File relationships

| Git-tracked source | Local or post-installation target | Target tracked | How it is produced |
|---|---|---:|---|
| `config/site.env.example` | `config/site.env` | no | copied and reviewed on each host; all Slurm nodes must use the same cluster UID/GID, node names and addresses |
| `config/lelab.env.example` | `/etc/robot-platform/lelab.env` | outside the workspace | copied by `15-install-lelab-platform.sh` on first installation, maintained by the administrator afterwards |
| `config/slurm/nodes.conf.example` | `config/slurm/nodes.conf` | no | filled in with each node's real `slurmd -C` output |
| `config/slurm/slurm.conf.template` | `config/slurm/slurm.conf.generated` | no | generated by `render-slurm-config.sh` from `site.env` and `nodes.conf` |
| `config/slurm/cgroup.conf` | `/etc/slurm/cgroup.conf` | outside the workspace | copied by the controller/worker installation scripts |
| `config/slurm/gres.conf` | `/etc/slurm/gres.conf` | outside the workspace | copied by the controller/worker installation scripts |
| `deploy/management/.env.example` | `deploy/management/.env` | no | `bootstrap.sh` generates a random database password on first run; the example only documents the fields |
| `apps/lelab/config/model-templates.json.example` | `/etc/robot-platform/model-templates.json` | outside the workspace | copied by the leLab installer on first run, maintained by the administrator afterwards |
| `deploy/systemd/*.service.example` | `/etc/systemd/system/*.service` | outside the workspace | copied by the corresponding role installation script |

## Initialize the local configuration

```bash
cp config/site.env.example config/site.env
cp config/slurm/nodes.conf.example config/slurm/nodes.conf
```

`config/site.env` is Git-ignored, so when deploying another node via `git clone` it has to be copied over or recreated separately. Do not copy the `deploy/management/.env`, the Munge key or the leLab SSH private key generated on the management node into this repository.

Generate the Slurm configuration:

```bash
./scripts/cluster/render-slurm-config.sh
```

The generated `config/slurm/slurm.conf.generated` is Git-ignored as well; distribute it to the workers over a controlled temporary channel and delete the temporary copies once the installation is done.

## Active configuration is never overwritten automatically

The following installation scripts use a "create only when the file does not exist" policy:

- `15-install-lelab-platform.sh` does not overwrite `/etc/robot-platform/lelab.env`;
- `15-install-lelab-platform.sh` does not overwrite `/etc/robot-platform/model-templates.json`;
- `bootstrap.sh` does not overwrite `deploy/management/.env`;
- `30-install-collector.sh` does not overwrite `/etc/robot-platform/collector.env`.

So editing an `*.example` in the repository does not propagate to already-installed hosts. Compare and edit the active configuration by hand, then restart the corresponding service.

In the current leLab node mapping, the left side is the Slurm NodeName and the right side is the SSH target:

```bash
LELAB_CLUSTER_NODES=mgmt01=192.168.100.202,gpu01=snorlax@192.168.100.215,gpu02=yang@192.168.100.216,gpu03=snorlax@192.168.100.217
```

The SSH user does not have to be the same on every node (`gpu02` uses `yang` above). This is a very long line: edit it in an editor, not with a one-line `sed` — a wrap introduced while pasting into the terminal makes `sed` report `unterminated 's' command`. After editing you must run `sudo systemctl restart lelab-platform`, because systemd only reads the `EnvironmentFile` at startup.

The full SSH setup is in [leLab cluster web](../docs/07-lelab-cluster-web.md); the full flow for adding a node is in [Adding a GPU node to an existing cluster](../docs/09-add-gpu-node.md).
